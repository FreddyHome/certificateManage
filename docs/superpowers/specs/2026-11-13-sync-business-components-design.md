# 同步任务三个业务组件重构设计

> 后续范围说明：本文的“三个入口”指本阶段业务组件；此后已增加独立 Shell 命令执行入口。现状与历史契约对照见 [2026-11-14 核对基线](../../../doc/requirements-design-review-2026-11-14.md)。

日期：2026-11-13  
状态：已实施并验证；IS keyStore 两步流程已按用户最新要求调整

## 1. 目标和范围

同步任务新增组件时，只提供「IS truststore 更新」「IS keyStore 更新」「TN 证书更新」三个业务组件。一个任务可按顺序添加多个组件，每个组件内部按固定步骤执行，用户不再手动连接通用文件、证书库和 HTTP 步骤。

沿用现有 Vue 3 / TypeScript 前端、Spring Boot 后端、服务器管理、客户和证书资产、加密秘密保存、定时调度、立即执行、快照及执行记录。已有通用任务可查看、编辑和执行，不自动改写、不删除已有配置。本轮不新增其他业务组件。

本文对用户未指定细节采用的规则均为设计建议，随本文一起接受审阅，不代表已得到确认。

## 2. 方案与现有约束

建议采用独立业务组件：前端用固定分区展示业务流程，后端负责组合读取、证书处理、远端更新，执行记录能区分内部阶段。

考虑过继续让用户拼接通用步骤。它能复用较多现有界面，但仍需要维护产物引用、请求模板和执行顺序，不能直接实现本次要求的三个组件入口，因此不采用。也考虑过仅提供三个模板并展开成通用步骤；展开后仍可能出现内部步骤被移动、删除和字段不一致的问题，因此不采用。

现有代码中固定 IS 重载请求还是旧 GET 接口，TN 固定组件的 URL 也与 `doc/rest-api.md` 不同。新组件按本次要求和该文档实现，旧任务保留原行为。当前数据库对步骤类型有约束，实施时优先使用现有步骤存储及独立业务标识区分新组件，不以更改旧类型含义实现兼容。

## 3. 编辑和配置方式

任务名称、说明、草稿／就绪、Cron、时区、立即执行及组件排序继续沿用。新增入口仅显示三个业务组件按钮。IS truststore 展示三个编号分区，IS keyStore 和 TN 各展示两个编号分区；无需用户设置内部步骤引用。

URL 输入表示所选 HTTP 服务器下的接口 URL，默认填入文档中的接口路径，并展示拼接后的请求地址。允许填写相对路径；如填写完整 URL，必须与所选服务器的协议、主机、端口和基础路径匹配，归一化为服务器下的路径，不切换到其他服务器。认证、TLS 信任及超时沿用服务器配置。

### 3.1 IS truststore 更新

**第一步：设置 truststore 来源**

| 字段 | 规则 |
| --- | --- |
| 来源 | 下拉选择 SFTP 或 HTTP，建议默认 SFTP |
| 来源服务器连接名 | 按来源类型筛选已启用的服务器，保存稳定服务器 ID |
| 文件全名 path | 必填，包含目录和文件名 |
| HTTP URL | HTTP 来源时展示，默认 `/restv2/wm.certificate:cert/keystore/get` |
| HTTP 方法 | 默认 GET，可选择 GET 或 POST；GET 不带请求体 |
| HTTP 请求头 | 默认 `Content-Type: application/json`，可添加普通请求头，鉴权由服务器管理 |
| HTTP 参数 | 默认 Query：`path` 自动引用文件全名；可添加其他普通查询参数 |

SFTP 固定执行读取，不显示上传、移动选项。HTTP 按接口一读取 JSON：`code="0"` 成功，取响应 `path` 和 Base64 `content`。组件内部统一输出 `{path, fileContent}`，`fileContent` 为解码后的原始字节。HTTP 成功响应必须包含非空 path 和合法 Base64 content；后续写回使用响应 path，SFTP 使用配置 path。界面显示上述输出说明，不展示原始文件内容。

**第二步：truststore 操作**

| 字段 | 规则 |
| --- | --- |
| truststore 密码 | 必填，执行时打开原库验证；须与目标原配置一致；留空保存表示保留已配置秘密 |
| 删除过期证书 | 默认不勾选 |
| 客户 | 必选，按客户 ID 筛选证书 |
| 证书用途 | AS2／HTTPS／通用 |
| 要导入的证书链 | 默认「自动选择到期最晚的可用链」，也可指定其他可用链 |
| 链中证书 | 展示各节点 CN、层级、序列号、到期时间，可单独勾选；默认全选，至少选一张 |

读取原库并验证密码后，在其内容上更新，不新建空库覆盖。自动识别 JKS／PKCS12，并保持原格式。保留未过期的原有条目；勾选删除时，按执行时刻逐一检查证书的 notAfter，仅删除已过期的受信任证书条目。如原文件含私钥条目，则拒绝作为 truststore 处理，避免删除或改写私钥。

导入节点别名自动采用「规范化 CN + 完整 DER SHA-256 指纹」，沿用现有自动别名规则。同一证书重复导入保持幂等；同名但不同证书由指纹区分。自动别名与已有不同证书条目冲突时失败，不静默覆盖。

**第三步：写入并重载**

选择 HTTP 目标服务器，填写 URL，默认 `/restv2/wm.certificate:cert/keystore/update`，填写 `keyStoreName`。来源为 HTTP 时建议默认目标为同一 HTTP 服务器；来源为 SFTP 时另选 HTTP 服务器。

固定 POST、JSON 请求头，请求体自动生成：

```json
{
  "keyStoreName": "用户填写的名称",
  "path": "第一步输出的 path",
  "content": "第二步生成的 truststore 原始字节的 Base64",
  "type": "trust"
}
```

type 只允许 key／trust；本组件固定为 trust，界面只读。响应按接口二的 code／message 判定。

### 3.2 IS keyStore 更新

按用户实施期间的最新要求，此组件删除来源读取步骤，采用以下两步。

**第一步：创建 keystore**

选择已启用、未归档、持有私钥的自有终端证书，不提供根证书或中间 CA 作为私钥条目。选择 JKS 或 PKCS12 格式，默认 PKCS12；填写与 IS 配置一致的 keystore 密码及私钥密码，均加密保存，编辑时留空表示保留。不要求八位，允许匹配现有目标系统的非空密码。

直接创建新的 keystore，仅包含所选终端私钥条目，并自动附上完整证书链，链按终端到根排序。私钥条目提供可选别名；留空仅采用终端证书的 CN 值，不追加指纹或其他编码。truststore 保留原自动别名规则。JKS 支持库密码与私钥密码不同；PKCS12 要求两者一致，并在界面提示。此组件不读取远端原库，不需要来源服务器，也不验证原库密码；密码与 IS 配置一致性在目标系统重载时确认。

**第二步：写入并重载（原第三步）**

选择 HTTP 目标服务器、填写更新 URL（默认 `/restv2/wm.certificate:cert/keystore/update`）、keyStoreName，以及写入文件全路径 `storePath`。固定 POST JSON，自动发送 `{keyStoreName, path: storePath, content: 第一步产物的Base64, type: "key"}`。文件路径只在此阶段配置。

### 3.3 TN 证书更新

**第一步：选择证书链**

选择客户、证书用途和证书链，默认「自动选择到期最晚的可用链」，可指定其他链。展示完整链供预览，TN 提交整链，不提供部分节点提交选项。

**第二步：更新证书**

选择 HTTP 服务器，填写 URL，默认 `/restv2/wm.certificate:cert/tn/update`。固定 POST、`Content-Type: application/json`。客户的 `externalId` 和 `idType` 自动映射为接口三的 `id`、`idType`，界面预览；缺失时提示先补齐客户信息。

```json
{
  "id": "客户 externalId",
  "idType": "客户 idType",
  "certChain": [
    {"index": 1, "certificateBase64": "根证书 DER Base64"},
    {"index": 2, "certificateBase64": "中间证书 DER Base64"},
    {"index": 3, "certificateBase64": "终端证书 DER Base64"}
  ]
}
```

链长不固定；按现有项目约定从根到终端，index 从 1 连续递增。文档尚未明确远端排序要求，此处沿用已有 TN 实现约定，需实际联调确认。

## 4. 证书选择规则

- 可用链：对应客户和用途的已启用、未删除、未归档终端资产，整条链当前在有效期内。自有私钥条目还必须存在匹配私钥。
- 默认按终端证书 notAfter 降序、资产 ID 降序选取；不存在可用链时明确报错。
- 自动模式在每次任务入队时选择并冻结证书，支持定时任务采用后续新增的最新链；手动指定模式始终使用指定链，不在失效时自动换链。
- truststore 自动模式默认导入完整链。用户取消某些节点勾选时，切换为指定链模式，按材料 ID 保存所选节点，避免自动换链后勾选错位。界面明确提示这一变化，并允许重新切换到自动整链模式。
- 修改客户、用途或手动链后重新计算节点选择，不沿用其他链的节点 ID。后端校验节点确实属于所选链。
- 入队快照冻结证书、客户对外标识、服务器版本、秘密版本及配置。执行前继续校验资产和服务器启用状态，沿用现有禁用阻断行为。

## 5. 执行、持久化及兼容

业务组件作为一个可排序单元保存；内部阶段由后端固定编排。保留原数据库中旧组件含义，新业务组件使用独立配置标识。实现可拆分校验器、证书库处理和远端读取职责，避免继续扩大通用执行器。

一个 IS 组件可能引用来源和目标两个服务器：任务依赖、禁止删除检查、入队服务器快照、连接版本和秘密引用必须记录两者，不能只记录目标服务器。证书和材料同样进入既有依赖与执行快照机制。

每个阶段提供开始、成功、失败记录及安全结果摘要：读取记录路径和字节数；处理记录库格式、删除和导入数量；HTTP 记录状态码和安全业务消息。整体组件失败后停止任务剩余组件，不自动重试远端写入。错误中明确阶段，写回成功但重载失败时保留失败信息，提醒检查远端实际状态。

文件原始字节、私钥、密码、Base64 content 和完整请求／响应正文不写日志或执行结果。普通任务详情仅返回密码是否已配置。读取内容和生成产物仅在内存中传递，继续使用单文件 10 MiB、单任务累计 25 MiB 的限制；HTTP 响应上限需覆盖 10 MiB 文件的 Base64 及 JSON 开销，先限制响应大小再解码。

HTTP 只有 2xx 且 JSON `code` 为字符串 `"0"`（兼容数字 0）才成功。非零 code、缺失 code、非法 JSON、非法 Base64、路径缺失和超限均失败；message 仅经安全处理后展示。

更新 `doc/rest-api.md` 中接口二的 type 说明为 string，合法值仅 key／trust，并补充实际采用的约定；接口鉴权继续由服务器配置提供。

## 6. 验证和验收

后端使用本地 HTTP 测试服务、SFTP 测试环境及真实证书库校验以下行为：

1. 两种来源的路径和文件内容传递，HTTP 的默认 GET、Query path、JSON 请求头及响应映射。
2. JKS／PKCS12 原库识别和密码校验；truststore 保留原有效条目、按开关删除过期条目、导入所选节点、别名稳定和冲突处理。
3. keystore 仅接受自有含私钥终端证书，生成库可重新打开，私钥可用、完整链正确；覆盖密码不同的 JKS 和 PKCS12 限制。
4. IS 更新的 POST 请求包含正确 keyStoreName、原 path、新 content 和固定 type；业务失败中断后续执行。
5. TN 自动最新与手动指定、客户标识和完整 DER 链报文；无可用链及客户标识缺失的错误。
6. 来源及目标服务器依赖和快照、秘密不泄漏、执行阶段记录和旧任务回归。

前端验证三个入口、来源联动、证书链默认与手动选择、节点勾选、密码保留、URL 和 type 展示，执行类型检查和生产构建。

代码实施并通过验证后，按项目 AGENTS.md 重新打包，沿用本项目工作目录、原 data 数据库和主密钥重启；检查首页及登录后的同步任务／服务器／证书 API。没有真实 IS／TN 环境时，以本地契约测试验证报文并明确真实重载和 TN 业务更新尚待联调。本阶段仅交付设计文档，不改代码或运行配置，不重启服务。

## 7. 审阅重点

以下是本设计补齐的主要规则，请重点确认：

1. truststore 修改原库；keystore 不读取来源，按选定格式创建仅含所选私钥及完整链的新库，路径在写入阶段配置。
2. 默认“自动最新”在每次入队时选链；部分勾选 truststore 节点会固定为当前指定链。
3. TN 链暂沿用根到终端排序；PKCS12 暂要求库密码与私钥密码相同，JKS 允许不同。
4. HTTP URL 绑定所选服务器，来源响应 path 传递给更新接口；IS 写入组件可另选目标 HTTP 服务器。
